# Управление сервером через `start.sh`

Скрипт рассчитан на Ubuntu 24.04, Bash и Docker Engine с Compose v2. Запускайте
его из корня проекта:

```bash
chmod +x start.sh
./start.sh check
./start.sh <команда>
```

Каждый этап выводится в терминал и записывается в `.start-logs/`. При ошибке
скрипт останавливается, показывает команду, строку, код возврата и путь к журналу.
После запуска контейнеров проверяются их состояние, Docker healthcheck и локальный
адрес `https://127.0.0.1/healthz`.

## Команды

### `prod`

Сохраняет локальные Git-изменения, выполняет `git pull --ff-only`, удаляет **все**
Docker-контейнеры сервера, неиспользуемые образы, сети, volumes и build cache.
Затем без cache собирает и запускает production. Команда разрушительная и требует
ввести `YES`.

### `prod_lite`

Сохраняет локальные Git-изменения, обновляет репозиторий и выполняет Compose
`up -d --build --force-recreate` без предварительного `down` и глобальной очистки.
Если образ изменился, Compose кратковременно пересоздаст соответствующий контейнер:
единственный экземпляр nginx не может гарантировать абсолютный zero-downtime.

### `dev` и `dev_lite`

`dev` обновляет Git, полностью очищает Docker на сервере и с нуля запускает
`docker-compose.dev.yml`. Требуется `YES`.

`dev_lite` обновляет Git и запускает существующее dev-окружение без очистки.
Исходники примонтированы в контейнер, поэтому Astro HMR видит изменения сразу.

### `git`

Если рабочее дерево изменено, скрипт создаёт:

```text
Mysor/YYYY-MM-DD_HH-MM-SS/
├── files/           # копии существующих изменённых и новых файлов
├── status.txt       # исходный git status
├── staged.patch     # staged-изменения, включая бинарные
└── unstaged.patch   # остальные tracked-изменения, включая бинарные
```

После резервирования рабочее дерево очищается и выполняется только безопасный
`git pull --ff-only`. При расхождении истории скрипт не делает принудительный
reset удалённой ветки, а останавливается с ошибкой. Удалённые локально файлы
восстанавливаются из Git; их удаление отражено в patch.

### `ssl` и `ssl_hard`

`ssl` проверяет формат локального X.509-сертификата и ключа, совпадение их
публичных ключей, срок действия не менее 30 дней и сертификат, реально выдаваемый
`mdgt.ru:443`. Код возврата `2` означает срок менее 30 дней.

`ssl_hard` принудительно запускает Certbot с `--force-renewal`, даже если текущий
сертификат ещё действителен. Это расходует лимит Let's Encrypt, поэтому команда
требует `YES`. В режиме `cocon` сначала нужно выполнить `cocon_off`.

### `info`, `down`, `del`, `reboot`, `non_d`

- `info` — состояния production/dev, 100 последних строк production-логов и
  использование диска Docker;
- `down` — корректно останавливает только Compose-проекты production и dev;
- `del` — удаляет **все контейнеры сервера**, но не images и volumes; требует `YES`;
- `reboot` — перезапускает production и снова проверяет готовность;
- `non_d` — запускает production в foreground, без `-d`; остановка через `Ctrl+C`.

### `arma`

ARMA собирает эталонные образы из текущего проекта и для каждого запущенного
production-контейнера проверяет:

1. совпадает ли ID запущенного образа с текущим собранным образом;
2. нет ли неожиданных изменений в записываемом слое (`docker diff`);
3. нет ли неожиданных bind mounts или volumes.

ARMA ничего автоматически не удаляет. При расхождении она завершится с ошибкой,
чтобы администратор сначала сохранил доказательства и просмотрел предупреждения.
Совпадение файлов не доказывает отсутствие атаки в памяти, ядре, внешнем томе или
соседнем процессе — это контроль целостности, а не полноценный EDR.

### `cocon_on` и `cocon_off`

`cocon_on` — аварийный режим изоляции. Контейнер nginx пересоздаётся:

- от UID/GID `101:101`, без root;
- с read-only root filesystem;
- без всех Linux capabilities, кроме `NET_BIND_SERVICE`;
- с `no-new-privileges`, лимитом процессов и маленькими `tmpfs`;
- с сертификатами только для чтения;
- без ACME-контейнера и без доступа к `/var/run/docker.sock`.

Перед включением нужен уже корректный локальный сертификат. Автоматическое
продление сертификата временно прекращается. `cocon_off` возвращает права ключа,
обычный Compose и ACME. Состояние сохраняется в `.start-cocon-enabled`, поэтому
последующие `prod_lite`, `reboot`, `info` и `non_d` учитывают включённую изоляцию.
Обе команды изменения cocon-режима запускаются через `sudo`, поскольку им нужно
безопасно изменить владельца закрытого TLS-ключа.

> Cocon уменьшает привилегии контейнера, но не является гарантией безопасности.
> После инцидента также обновите ОС/Docker, смените секреты, изучите журналы и
> пересоздайте сервер из доверенного образа.

## Автоматизация и проверка

Разрушительные команды можно подтвердить неинтерактивно:

```bash
./start.sh prod --yes
# или
START_ASSUME_YES=true ./start.sh prod
```

Перед первым применением и после обновления запускайте:

```bash
./start.sh check
```

Проверяются Linux, Git, доступ к Docker daemon, Compose v2, Bash-синтаксис,
все Compose-конфигурации и Git worktree. Для полного теста запуска используйте
сначала `dev_lite`, затем `info`; destructive-команды на рабочем сервере нельзя
безопасно имитировать, поскольку их назначение — реально удалять Docker-данные.

Изолированный интеграционный тест резервирования Git (не затрагивает Docker):

```bash
bash tests/start-sh-git-test.sh
```
